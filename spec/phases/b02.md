Completed 2026-09-26. Evidence: `spec/evidence/b02-completion-2026-09-26.txt`; design: ADR 0009.

- **Delivered:** `payment-api` serves `POST /api/v1/payments` (headers `Idempotency-Key` and `X-Correlation-ID`; `202` plus `Idempotent-Replayed`), `GET /api/v1/payments/{id}/receipt` and `GET /api/v1/commands/{id}`, per `contracts/openapi/v1/payment.json`. The service validates requests with kin-openapi against the embedded bundle and generates its boundary with oapi-codegen (`make openapi-generate`). Payment migration 0002 adds the aggregate, immutable instruction, per-version history, idempotency records (no TTL), commands, audit, domain events + outbox, and `workflow_dispatch`, with database guards. `PaymentReceived` v1 is committed with every new receipt. Customer account ownership is checked through the Core Banking port using the new `payment-service` client-credentials identity.
- **Checks passed:** full Go gate; live PostgreSQL atomicity at all 8 failure points, replay/409, 16-way concurrent duplicates, stale-version conflict, submission/cancellation claim race and DB guards; end-to-end API smoke, including restart survival with pending dispatch and replay during a Core Banking outage; I02/I03/B01 regression; govulncheck clean.
- **B03 can rely on:**
  - `app.domain_events` rows: `schema_version` 1, `source` `payment-api`, and a per-aggregate `event_sequence` starting at 1, aligned with `aggregate_version`.
  - `app.outbox` rows (`published_at` NULL, `delivery_attempts`, `last_error`) waiting for the relay. Workflow dispatch has separate delivery state.
  - The `PaymentReceived` payload schema, and `customerId` in the event for customer-scoped projections.
- **B04/B06 can rely on:**
  - `storage.Store.Apply` as the only versioned change primitive. It locks the row, the domain mutation checks the expected version, and it appends history, events, outbox and audit.
  - The domain operations `Transition`, `ClaimSubmission`, `ClaimCancellation` and `AssignExecutionOwner`.
  - `workflow_dispatch` rows (`PENDING`, `workflow_id` = `payment/{paymentId}`, lease columns, `next_attempt_at`) for the leased dispatcher.
  - Execution owner IDs of the form `execution/{paymentId}/{product-kebab}`.
  - The payment worker can reuse `platformruntime.LoadServiceClient` and the `payment-service` identity for Core Banking calls.
- **Nonblocking limitations:**
  - No outbox relay (B03) and no dispatcher or workflow start (B06).
  - No list/search endpoint; B03 projections provide it.
  - `commands.command_type` is only `SUBMIT_PAYMENT`, and B04 extends it.
  - Accepting a new instruction requires Core Banking account lookup; replays do not.
  - Realms imported before B02 need `make oidc-sync`.
  - The CI infrastructure job does not run the B01/B02 live checks.
