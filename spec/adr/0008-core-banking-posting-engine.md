# ADR 0008: Core Banking posting engine

Date: 2026-09-26. Status: accepted for B01.

## Context

Foundation Section 5 requires an independent Core Banking authority with
booked/available balances, atomic reservations without overdraft, balanced
immutable postings, linked reversals, suspense/settlement accounts and stable
operation IDs. Section 7 makes Core Banking the owner of its posting event
journal/outbox, and Section 8 lists the Core Banking port operations. Payment
phases (B02 onward) call this port across a database boundary and must be able to
recover a lost reply without a second financial effect.

## Decision

- **Storage and queries.** `corebanking` migrations 0002–0003 own accounts,
  operations, holds, posting journals/entries, posting events and an outbox.
  Queries are generated by pinned `sqlc` v1.31.1 into `storage/coredb` and run on
  `pgx/v5`; transactions and every accounting rule stay in `service.go` and the
  pure `domain` package.
- **Operation identity.** Every mutation carries a caller-supplied UUIDv4
  operation ID. A transaction-scoped advisory lock on that ID serializes retries;
  the stored SHA-256 of the canonical financial fields decides between replaying
  the original hold/posting and returning `409`. Operation rows are immutable and
  never expire, and `GET /operations/{id}` recovers the result after a lost reply.
- **Balances.** Accounts store the booked balance; available balance is booked
  minus `ACTIVE` holds and is only computed, never stored. Reservations lock the
  account row and are refused unless they fit the available balance. Postings lock
  the consumed hold, then the accounts in sorted ID order (deadlock-free), apply
  each account kind's normal side, refuse any negative balance, and re-check that
  customer balances still cover remaining active holds.
- **Hold consumption.** A posting may consume one active, unexpired hold only
  when the held account carries exactly one matching debit total in the hold's
  currency. Consumption, balance changes, journal, entries, event and outbox row
  commit in one transaction.
- **Reversals.** A reversal is a new posting with its own operation ID, the exact
  opposite entries and `reversal_of_posting_id`; a unique constraint permits one
  reversal per original, and reversals cannot themselves be reversed. It is the
  Scenario B compensation primitive only; returns (Scenario C) and inbound credits
  (Scenario E) are ordinary evidenced postings chosen by the caller.
- **Database guards.** Triggers make operations, journals, entries and events
  append-only and restrict holds to a single `ACTIVE → CONSUMED|RELEASED`
  transition. A deferred constraint trigger rejects any journal that does not
  balance per currency, so even a direct SQL write cannot commit an unbalanced
  posting.
- **Events.** Each posting appends one `CoreBankingPostingCommitted` v1 event
  (`contracts/events/v1/core-banking-posting-committed.schema.json`) and an
  unpublished outbox row. B03 adds the relay and delivery state.
- **Port.** `contracts/openapi/v1/core-banking.json` specifies the port under
  `/integrations/v1/core-banking`. It requires a bearer token with audience
  `core-banking-service` and the `internal_service` role. Handler responses are
  tested against that document.
- **Fixtures.** Local seeds open the synthetic SGD accounts through one balanced
  opening journal (dataset `local-b01-v1`), not by writing balances directly.

## Consequences

Callers must persist their operation ID before calling and reuse it on every
retry; a `503` or timeout is not evidence that no posting occurred. Suspense,
clearing and settlement accounts cannot go negative, so tests and fixtures must
fund settlement accounts through balanced opening journals. FX, fees, overdrafts,
partial reversals and a complete general ledger remain outside the foundation.
Outbox publication and statement pagination cursors are deferred to B03.

The architecture test now forbids domain packages from directly importing `net`
or `database/*`, rather than rejecting those packages anywhere in the transitive
graph. That's because maintained value libraries (for example `gofrs/uuid`) implement
`database/sql` interfaces themselves. Temporal and outer GTB packages remain
forbidden transitively.

## Amendment (2026-09-27): no JSON tags on generated rows

`sqlc.yaml` no longer sets `emit_json_tags`, for both the `corebanking` and the
`payment` entries. The generated row structs (`coredb`, `paymentdb`) are
persistence types only. sqlc maps columns by position in `Scan`, so the tags were
never read, and no service encodes a row directly. HTTP and event payloads map
rows to domain or contract types first, which keeps wire formats independent of
column names. Regenerated with `make sqlc-generate`; generated code has no
behavioural change.
