Java to Go Payments Cheatsheet

Java → Go, for a payment platform

A working reference for a Java engineer on a Go rewrite: what to unlearn, what replaces the Spring toolkit, and where payments code needs extra care.

payments-criticalcommon trap

The verdict

Go suits payments well. The bigger risk is the rewrite, not the language.

Payment platforms are I/O-bound orchestration with strict latency and reliability needs: cheap concurrency, small binaries, predictable performance and auditable code all help. Explicit errors and transactions are a feature when money moves.

Watch for: lost edge cases buried in the Java code, weaker type-level domain modeling, and a team writing Java-shaped Go.

Push for a safe migration

  • Strangler cutover by payment flow or merchant segment, never big-bang.
  • Shadow traffic: run Go alongside Java and diff the outputs.
  • Reconciliation reports between both systems before each switch.
  • Mine the Java code for scheme quirks, retry rules and past incident fixes; turn them into Go tests first.
  • Most of what feels missing is Spring, not Java. Go makes those decisions visible in code.

Mindset shifts

DI still exists, by hand

Constructors take interfaces; main builds the graph. Reach for google/wire or uber/fx only if the graph gets large.

func main() {
  db := mustOpenDB(cfg)
  ledger := ledger.NewRepo(db)
  acq := acquirer.NewClient(cfg.URL, httpClient)
  svc := payment.NewService(ledger, acq, clock.Real())
  http.ListenAndServe(":8080", api.NewRouter(svc))
}

Interfaces live with the consumer

The caller declares the small interface it needs; implementations satisfy it implicitly. No FooService + FooServiceImpl pairs up front.

// in package payment
type Authorizer interface {
  Authorize(ctx context.Context, r AuthReq) (AuthResult, error)
}

Composition over inheritance

Struct embedding and small interfaces replace abstract base classes. Model payment methods as separate types behind one interface, not a hierarchy.

Package by capability

payment, ledger, refund, not controller/service/repository. Plain functions where no object is needed. Boring code is the goal.

Errors carry business meaning payments

declinedValid outcome. Record it, don't retry.
retryableTimeout or 5xx before sending. Retry with the same idempotency key.
unknownTimed out after sending. Status inquiry or reversal, never a blind retry.

Use typed or sentinel errors. Wrap with fmt.Errorf("authorize: %w", err); check with errors.Is / errors.As.

context.Context

  • First argument of every function that does I/O, through every layer.
  • Carries deadlines, cancellation and trace IDs.
  • Set a deadline on every outbound call.

Money & state payments

Money

Never float64.

int64 minor units + currency code inside a Money type; shopspring/decimal for FX or fractional precision. Block arithmetic across currencies.

State machines without sum types

Named type, one transition table, one function that changes state. Add the exhaustive linter for switches.

Transactions & consistency

  • No external calls inside a DB transaction.
  • Transactional outbox for events.
  • Idempotency key + unique constraint on every externally triggered operation.

Traps for Java devs traps

Concurrency

  • A panic in any goroutine kills the whole process. Recover at goroutine boundaries you start.
  • Goroutine leaks: unread channels, calls without timeouts.
  • Run tests with -race in CI.
  • Fan-out with errgroup, not hand-rolled WaitGroups.

Language

  • Writing to a nil map panics.
  • An interface holding a nil pointer is not == nil.
  • append can share the underlying array between slices.
  • Loop-variable capture: fixed in Go 1.22, still in older code.
Your edge as a Java engineer: domain thinking, transactional rigour and DDD instincts. Bring the principles; express them in Go's idioms, not Java's patterns.
